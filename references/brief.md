# Steps 0–2: setup, brief, reference

## Step 0 — Setup (once)

```bash
node <skill-dir>/scripts/preflight.mjs
```

One call, a few seconds (longer on a cold `npx` cache; ≤ ~80 s with `--start`): Node, ffmpeg, HyperFrames, this skill's own clone (behind `origin/main`?), VoiceStudio (backend, TTS model, speech-to-text model, watermark), ElevenLabs (tier and quota, never the key; paid, optional), a stock-video key. `<skill-dir>` is this skill's folder. Fix only what it reports:

- **Voice MISSING** → `voice.md` "Setup" (VoiceStudio install, models, the outside-the-backend download, activating speech-to-text; ElevenLabs key rules). Ask before installing anything; state sizes and licences.
- **VoiceStudio states** — act on the note preflight prints, never on a guess. Never write your own polling loop: rerun preflight.
  - **STOPPED** (macOS app installed, not running) → `node <skill-dir>/scripts/preflight.mjs --start` opens it and waits ≤ 60 s, inside a default tool timeout. If the note says **never launched**, the first launch downloads several GB: ask first (autonomous: that is an install offer — skip it).
  - **BUSY** (running but not answering: an inline download, another session's job, a backend restart) → wait a minute and rerun; never restart it, reinstall or switch engines. Still BUSY after ~3 reruns a few minutes apart → tell the user, carry on with Steps 1–3 and recheck before Step 4.
  - **DOWN** (Linux/Windows, or another local port) → ask whether it is installed: open it, or install with consent. **UNREACHABLE** (a remote `--vs-url`) → "nothing listens": ask the user to start it on that machine; "not answering": ask, and never have a backend restarted that may be running a job. **CONFLICT** → something else holds the port: tell the user.
  - A **WARN "refused the read"** (a remote backend behind an API key or loopback-only settings): dalang sends no key — tell the user (`voice.md` "Setup").
  - A **WARN "could not read / list"** → rerun; it never means missing.
  - A remote backend: pass the same `--vs-url` to every preflight rerun and to `tts_timestamps.mjs`.
  - `--start` checks VoiceStudio only; the rest of the first run still stands.
- **HyperFrames MISSING or out of date** → asked in Brief Call 0. New skills load after Claude restarts.
- **DALANG skill WARN (behind `origin/main`, or `pinned at vX (detached), newest release is vY`)** → asked in Brief Call 0 (autonomous: pull it yourself only when the note says `N commits behind` and has no "uncommitted" or "diverged": `git -C <skill-dir> pull --ff-only`, log it in `PRODUCTION.md`; a **pinned** clone is the user's choice, so log the WARN and continue, never pull or check out on your own). A pinned clone is detached: `pull --ff-only` fails there, so run the note's own command (fetch tags, check out the newest release, the README's update), never a pull from `main`. After an update, re-read `SKILL.md` (the copy you loaded is stale) and this Step 0 section, then rerun preflight. Dirty or diverged: report it, never stash, reset or pull on your own. **"could not check"** (offline, timeout, `git` missing or refusing the folder, e.g. another owner, a `.git` git skips, any git read that failed) → rerun; it never means up to date, behind or "not a clone", and never a reason to clone again; `INFO … not a git clone` is only a folder without a `.git`. `--check-skill` rechecks this row alone.
- **Stock video WARN** → asked once, in Brief Call 0, for a free `PEXELS_API_KEY` or `PIXABAY_API_KEY`. Without one the hero still comes from the user's photos and footage or Commons (`visual-direction.md` §1 rungs 1–2), and a subject that must act on camera with no footage is built in three.js. DALANG installs no image, video or music generator: stills, footage and music come from real licensed sources and three.js. HeyGen (stock photos, image-to-video) uses metered credits: mention it only as optional and paid.
- **Licences to mention once:** VoiceStudio's default OmniVoice weights are non-commercial (CC-BY-NC); so is the ElevenLabs free tier. For a monetised video, the user needs a commercial-OK voice (`voice.md` "Licence"). Preflight's `Voice:` line carries this caveat (with `--json`, the TTS model note); read the whole output, never grep it. Tell it in the plain text before the first Brief call: a notice, not a question. It is about the model that will speak (preflight's TTS model note, or the model the Brief picks): when that voice is non-commercial, say so in Call 0 and again at Gate 2, **even when the user said not to ask or to run unattended** — a statement, never a question, so it does not break that instruction.

Every setup choice the user must make (DALANG update, skills update, stock key) is a question in Brief Call 0, never only a line in `PRODUCTION.md` (autonomous: nobody to ask — log it, per SKILL.md).

Create `video/<topic-slug>/` and log a one-line preflight summary with `state.mjs log` (it creates `PRODUCTION.md`): the statuses, never the saved voice list.

## Step 1 — Brief (always via AskUserQuestion)

**Topic first.** If the user named none, ask in plain text. Never guess a topic.

**The user may bring material** — a finished script, a voice recording, photos, a reference video. Use what they bring and skip the questions it already answers: a script replaces Step 3's writing (still convert it to `narration.txt` and show it at Gate 1); a recording replaces the voice question and Step 4's generation (`--from-audio`). Before using someone's recorded voice, confirm the speaker gave permission; then pass `--own-recording` (a human recording the user may use, never TTS output). A video from someone else's channel is only a reference to measure (Step 2), never material to reuse. When the subject is a machine they may own (a car, a bicycle, an appliance, a tool), ask for 3–5 phone photos of it (the part the video is about, close and wide): the film must show their real machine, part for part.

**A voice named in the request** ("narrated by <name>") → match it against preflight's `Voices` line and save it as `voice` in `BRIEF.md`. While VoiceStudio is not OK (no such line), save the name as given and match it once preflight reads OK, before Step 4; the Brief goes on. A match needs no "which voice?" question in Step 4, which still samples it for pace; the Call 0 engine question stays. Never search earlier videos' files for it. No match, or the line WARNs → rerun preflight; still none → say so and offer the saved profiles, a designed voice, or a clone only with the speaker's permission (`voice.md` "Clone").

Then AskUserQuestion: Call 0 only when setup left a choice, then Calls 1 and 2 (4 questions each at most), and Call 3 when it applies. Ask about the platform **even if the user named one** ("YouTube" can be Shorts or landscape); put what they said first, marked "(Recommended)". Nothing named, or an answer of "no preference" → recommend / use the Autonomous-mode default for that question. Context the user should read goes in plain text before the call (the tool has no intro field): no reference video unless they have one (then Step 2); the voice is asked in Call 3 when there is more than one sensible choice, else picked by audition in Step 4 (unless named, above); the engine, when only one is ready.

### Call 0 (only when preflight left a choice; skip it otherwise)
- **HyperFrames skills** (MISSING or out of date) — "Update now (Recommended)": `npx hyperframes skills update`, loaded at the next Claude restart: right after the Brief, before Step 5 (style frames load `/hyperframes`); resume with `state.mjs`; "Not now" (MISSING: no build until it is fixed).
- **DALANG update** (DALANG skill WARN, behind, or pinned to an older release) — "Update now (Recommended)": the command in the note (`git -C <skill-dir> pull --ff-only` for a clone on `main`, clean and fast-forwardable only; for a pinned clone the fetch-tags and check-out-the-newest-release command, never a pull), then re-read `SKILL.md` and go on; "Not now": say what a run may miss (fixes already in `origin/main`). Ask it first: the other setup choices may be answered by the pulled text.
- **Stock footage** (Stock video WARN) — "Add a free key (Recommended)": the user signs up at pexels.com/api or pixabay.com/api and adds `export PEXELS_API_KEY=…` (or `PIXABAY_API_KEY`) to their shell profile. The running session may only see it after Claude restarts from a new terminal (or after the profile is sourced), one restart with the skills update, right after the Brief and before Step 5 sources footage; rerun preflight then to confirm. Still WARN → Commons and three.js, and if the chosen Realism leaned on stock footage, tell the user before Step 5. Never ask for the key in chat or write it to project files. If they pick this, plan Call 1 as if the key exists. Option 2: "No key — Commons and three.js".
- **Voice engine** (only when preflight shows ElevenLabs as `PAID`: a valid key) — "VoiceStudio — free, runs locally (Recommended)"; "ElevenLabs — paid cloud" (never recommended; free tier is non-commercial and small).

### Call 1
1. **Platform** — YouTube Shorts (9:16, 1080×1920, ≤ 3 min, hook in 1–2 s) · Instagram Reels (9:16, ≤ 3 min, taller bottom overlay) · YouTube landscape (16:9, 1920×1080) · Instagram feed (4:5, 1080×1350, ≤ 60 s, often muted). TikTok and 1:1 via "Other".
2. **Language** — the user's language "(Recommended)", English, and one other likely language for this topic or audience; the rest via "Other". Store the ISO 639-1 code.
3. **Angle** — **built from the topic**, 3 options, e.g. "Question answered with data", "Myth vs fact", "Story with a character", "Dialogue scene between characters (no narrator)", "Step by step", "A vs B", "Recommendation per type of person". Angles with people acting or speaking on screen need real footage of people (`visual-direction.md` §1 "People"; a generated clip only on paid request); without a source, say so in the option.
4. **Realism** — the one choice that decides the whole visual pipeline, so explain it. Two options, each with a `preview` sketching one frame of *this* topic in that realism:
   - **Hyperreal — looks like real footage.** Real photos and footage, PBR 3D lit like a product film (generated stills or clips only on paid request). Most convincing when the viewer judges the real thing (products, places, food, people, "which one to buy"). Slower: sourcing, reality checks, heavier renders. Looks A, B, E, F, plus D and H.
   - **Stylized — a premium animated film.** Real shapes and real materials in a designed palette and framing: a studio diorama (a designed miniature on a light, warm set, separated from it by its dark parts and contact shadow, a few small accents each with a job, like the best-loved three.js scenes) or toon with ink lines: very easy to watch, the idea reads at a glance, built in three.js, renders in seconds. Still true to how the thing works. Best for mechanisms, science, things too small, large or hidden to film, kids, stories. Looks C, G, I, plus D and H.
   Put "(Recommended)" on Hyperreal when the real look is the point, on Stylized when the idea is the point. Type (D) and data (H) carry either realism: for an idea with no physical subject (an economic force, a law, a feeling) say so in the question and recommend them. Save as `realism` in `BRIEF.md`. When there is no stock key (Call 0) and the user brought no photos or footage, the Hyperreal option and its preview name where the moving subject will come from (Commons stills and clips, three.js), never footage there is no source for; recommend Hyperreal then only if those cover the subject.
   For a 3D set, record from the topic (ask only when it is unclear): **`condition`** for any made thing in it (a room, a machine, a street, a battery) — `lived-in` by default, `new`, or `worn` (peeling paint, scuffs, grime, corrosion: only when the topic is about age, neglect, hardship or history); and, only when the set has rooms or furniture, **`interior`** — `american-japandi` by default (honey bamboo and light oak, warm white walls, a white or navy panel door, oatmeal linen, a ceramic or two, American home motifs: Shaker panels, buffalo check, ticking stripe, a braided rug), another when the topic names a place or style.

### Call 2 (its options follow the platform)
**fps follows the platform** (plain text before the call, no question; save it in `BRIEF.md`):

| Platform | fps |
|---|---|
| Shorts, Reels, TikTok, Instagram feed | 30 |
| YouTube landscape | 30; 24 only for a film look the user picks (offered as its own Energy option, item 7), with the blur rule of `camera-motion.md` §10 |
| anything else | 30 |

Those platforms play at 30 (Reels caps there), so 24 repeats one frame in four and judders on pans. Never 60: double the render time, re-encoded to 30.

5. **Duration** — 9:16 → 30–45 s, 60 s, 90–120 s, 2.5–3 min; 16:9 → 60–90 s, 2–3 min, 5 min; 4:5 → 15–30 s, 45–60 s. Narrative pacing is strongest at 30–90 s; above 3 min, one composition per section.
6. **Visual style** — read `looks.md` and `visual-direction.md` §5. Offer the **looks of the chosen realism that best fit this topic** (up to 4), recommended first; name the others in the question text so "Other" reaches them. Every option gets a `preview`: a short sketch of one frame of *this* topic in that look (the real subject and its source, set, the ground colour and how the hero separates from it, light, type, motion), never a banned default (`looks.md`, `visual-direction.md` §5). A reference the user liked steers the palette: use its `## Palette` in `reference-measurements.md` when Step 2 measured one.
7. **Energy** — "Modern balanced", "Calm cinematic", "Punchy social" (`visual-direction.md` §3); "(Recommended)" goes on Punchy for 9:16 under 60 s, else on Modern balanced. YouTube landscape adds a fourth option, "Calm cinematic, film look (24 fps)" (blur per `camera-motion.md` §10); only picking it saves fps 24, else 30.
8. **Audience** — General public, one main idea "(Recommended)"; Students; Professionals/enthusiasts.

### Call 3 — Voice

After Call 2: its recommendation follows the Audience answer. Never fill `voice` from a saved profile on your own: the user would meet it for the first time in the Gate 1 summary. Ask it when preflight's `Voices` line lists two or more saved profiles, or one saved profile and the audience points away from it (a clone of the user for a public or brand channel). Skip it when a voice was named in the request (above), the user brings a recording, or there is one profile and no audience reason (Step 4 asks which to try then). A `Voices` line that WARNs is not "no profiles": rerun preflight first. Options (4 at most): each saved profile by name, a clone of the user marked "(your voice)" (when the user said so, or the name is theirs); "Designed narrator — describe gender, age, style"; further profiles via "Other". "(Recommended)" follows the audience: a public or brand channel (an audience the user does not front personally) → the designed narrator, or a saved profile licensed for that use; a personal channel where the user is the face → their own voice, if saved. Name the voice's licence when it is non-commercial (`voice.md` "Licence"). Save `voice` as the profile id, or `design: <description>` (Step 4 auditions 2–3 designed voices from it). Autonomous mode: the recommended option, logged.

### Save the brief

Save everything in `BRIEF.md`: topic, platform, ratio & resolution, fps (from the platform, table in Call 2), duration, narration language (ISO code), angle, realism, look, energy, audience, voice engine, voice model (VoiceStudio: the active one unless the user picks another), voice (a named profile id, `design: <description>`, or `audition`). Every later step reads format and language from it, not from memory; a mid-way change updates `BRIEF.md` first.

Step 2 (optional, measuring a reference's craft): `measure-reference.md`.
